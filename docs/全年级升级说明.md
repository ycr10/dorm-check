# 单班系统升级为全年级系统

本文针对**已有单班版本、已有真实名单和历史记录**的部署。以下操作由站点维护人员在维护窗口执行；本轮没有连接或修改你的服务器。本地隔离 SQLite 测试不能替代目标服务器的 MySQL、PHP-FPM、HTTPS 和计划任务验收。

## 一、升级后的变化

- 系统管理员管理全年级、班级和账号；班委由管理员分配一个或多个班级，后台只返回其获授权班级的数据。班级授权变更后，该账号需要重新登录。
- 不再创建或使用宿舍长登录角色。旧宿舍长账号迁移后停用，旧操作记录保留；宿舍负责人仍是名单中的人员，无需账号。若本人之后需要班委账号，管理员须重新核实并创建相应管理账号。
- 每次选择一个班级导入 UTF-8 CSV。同一物理宿舍可跨班，负责人在便捷入口一次登记整寝；班委后台仅管理自己获授权的学生。管理员可在“名单与授权 → 班级与账号”交接宿舍负责人。
- 08:00 默认日期切换和单日筛选保持不变。跨班混住时，班级日报中的寝室数是**包含该班成员的物理寝室数**，人员与进度仅按获授权范围统计。
- 便捷入口仍**不验证身份**：知道负责人学号和房号的人可能冒充填报并看到整寝最低限度的成员信息。班级后台隔离不等于便捷入口身份认证。

## 二、先备份，确认维护范围

1. 选择站点维护时间，确认项目路径、所使用的配置文件和数据库。默认配置是项目目录的 `config/local.php`；若设置 `DORM_CONFIG`，以指定文件为准。CLI 与网站 PHP-FPM 必须连向同一个本站数据库。不要在聊天或群里发送配置、数据库密码、`app_key`、备份密钥或正式名单。
2. 在公开目录外备份本站**旧版完整代码、配置、数据库和存储目录**，确认备份可读取，并先在独立环境演练。数据库备份和加密 `.dcb` 仍包含敏感资料，不能放到 `public/` 或公开仓库。无需清空数据库、重新安装、重新初始化或重新导入已有名单。
3. 保留旧版程序及其可用备份，以便必要时恢复。先检查两步验证指定账号：如果当前指定的是将被停用的旧宿舍长账号，请在**旧版后台**先按原流程改为已激活的管理员，再开始升级。若尚未指定账号，迁移会沿用现有的管理账号验证策略。
4. 按[宝塔面板部署教程](宝塔面板部署教程.md)确认本站 PHP CLI、FPM、扩展和站点级参数。以下路径只举例，必须按实际路径替换；不要修改共享 PHP 全局配置或擅自重启、重载共享服务。

下面的命令以旧项目根目录 `/www/wwwroot/dorm.example.com` 和宝塔 PHP 8.5 CLI 为例。先由维护人员确认 `/root/dorm-check-backups/` 是已存在、只允许维护人员访问的私有目录；输出文件必须是新文件。备份密钥必须是独立的 32 字节随机值的 Base64，并离线保存；它不是 `app_key` 或数据库密码。以下读取方式不会把密钥明文写进命令历史，但仍应保护终端及进程环境：

```bash
cd /www/wwwroot/dorm.example.com
PHP=/www/server/php/85/bin/php
read -r -s -p '输入已离线保存的备份密钥（Base64）：' DORM_BACKUP_KEY; printf '\n'
export DORM_BACKUP_KEY
"$PHP" -d session.upload_progress.enabled=0 -d session.serialize_handler=php bin/console.php maintenance:on
backup_path="/root/dorm-check-backups/before-grade-$(date +%Y%m%d-%H%M%S).dcb"
"$PHP" -d session.upload_progress.enabled=0 -d session.serialize_handler=php bin/console.php backup --output="$backup_path"
```

只有确认备份命令成功、文件存在且已保存所需密钥后才继续。备份失败时不要上传代码或迁移；请先排查。计划任务遇到本站维护标记会暂停，恢复后按原调度规则补跑。不要把示例路径直接用于其他站点。

上述清单包含当前程序的完整业务代码和公开资源，适用于服务器尚未上传完整 08:00 单班版本的情况；不要混用旧版本文件。`public/router.php` 仅用于本地开发服务器，不是生产入口，生产环境只允许指定 API PHP 入口。`docs/`、`tests/` 和 `templates/` 可按需放在项目根目录，**不能暴露到 `public/`**。不要覆盖真实的 `config/`、`storage/`、数据库、密钥、名单或备份；也不要上传旧的开发数据库。

上传后，新版 API 在数据库尚未迁移时会返回 `MIGRATION_REQUIRED`，不会自动初始化或清库。不要此时解除维护。

## 四、先预检，再显式迁移

仍在项目根目录、使用与网站一致的本站配置运行：

```bash
"$PHP" -d session.upload_progress.enabled=0 -d session.serialize_handler=php bin/console.php migrate:preview
```

- `ready: true` 表示本项目预检未发现阻止迁移的班名／两步验证问题；它**不是** MySQL、备份恢复或全流程的生产验收证明。
- 如果报告旧宿舍长是指定两步验证账号，不要强行迁移。恢复旧版代码并保持原库，按原流程将指定账号改为已激活管理员，再重新安排升级。
- 如果报告历史班名不一致，先在隔离副本核实 `historical_class_names`：其中可能包含当前名单、住宿历史、冻结名册和固定日报里的班名。不要把未经核实的不同班级合并。

确实需要映射时，维护人员在**公开目录外**建立只读给维护账号的 UTF-8 JSON 文件，例如 `/root/dorm-check-backups/class-map.json`。下面只是虚构示例：每个预检列出的历史名称都必须有一项；当前班级必须映射到它自己的名称。不同旧名称可经核实映射到同一班，实际不同班则映射到不同名称。不要复制示例班名直接用于真实数据。

```json
{
  "当前示例班": "当前示例班",
  "旧示例班名": "当前示例班",
  "另一历史班": "另一实际班"
}
```

重新预检并逐项核对返回的 `mapping`，必要时修正文件后再预检：

```bash
"$PHP" -d session.upload_progress.enabled=0 -d session.serialize_handler=php bin/console.php migrate:preview --map-file=/root/dorm-check-backups/class-map.json
```

文件可能包含真实班名，应按私有运维资料保管，不上传到网站或公开仓库。预检通过后，确认正在维护模式且已完成备份，再执行对应的一种命令：

```bash
# 不需要映射时
"$PHP" -d session.upload_progress.enabled=0 -d session.serialize_handler=php bin/console.php migrate --confirm=GRADE

# 需要映射时，使用刚才核对过的同一文件
"$PHP" -d session.upload_progress.enabled=0 -d session.serialize_handler=php bin/console.php migrate --confirm=GRADE --map-file=/root/dorm-check-backups/class-map.json
```

完成后应返回 `schema_version: 2`。迁移保留固定日报原文和旧住宿历史，旧班委默认仅获原班授权；其他班级需管理员核实后显式分配。MySQL 的建表语句可能独立提交，不能把升级当成全部 DDL 的单一原子事务；失败时保持维护，先查看错误、保留现场，不要重复初始化或手工清表。程序会检查现有表并支持重试，但实际 MySQL 升级和中断恢复仍需先在副本演练。

## 五、验收和重新开放

1. 在独立的 MySQL 副本先验证迁移前后的班级、学生、历史日报、旧宿舍长账号状态、管理员／班委范围，以及版本冲突、导出和备份恢复。确认服务器 CLI、FPM、HTTPS、Argon2id、计划任务在目标环境正常；本机 PHP WASM 的结果不能证明这些项目。
2. 按原有维护流程确认站点至少有一名符合 TOTP 策略的有效管理员。完成准备后执行：

   ```bash
   "$PHP" -d session.upload_progress.enabled=0 -d session.serialize_handler=php bin/console.php maintenance:off
   ```

3. 重新登录管理员和班委，在“名单与授权 → 班级与账号”核实每位班委的班级权限；未分配班级的班委不应看到学生数据。按班导入时先预览，缺失负责人或存在冲突必须核实；测试跨班混住、一键全到、当前负责人交接以及其他班越权拒绝。
4. 验证所选日期只显示当天、07:59:59／08:00 默认日期、固定日报与 Excel 的班级范围、备案显示和本站计划任务；强制刷新浏览器缓存。若有问题，保持或重新进入维护模式，停止使用，不要反复导入名单或清库。

## 六、备份恢复和回退边界

新版备份包含班级、班名映射与班级授权。恢复新版备份需要维护模式和独立备份密钥；成功恢复后旧密码、会话、一次性码、TOTP／恢复码及**班级授权**都会失效，维护模式仍开启。管理员需按[部署教程](部署教程.md)受控恢复账号、重建班级授权、核实名单后再确认开放。备份配置不会自动覆盖当前配置。

旧单班结构版本 1 的 `.dcb` **不能直接覆盖恢复到年级版结构版本 2**。如需从旧备份迁移，先用对应旧版源码在独立的同类型数据库恢复并核实，再按本说明预检与迁移；不要指向正式库做首次演练。

回退到旧版需要同时考虑代码和数据库结构：只换回旧源码而保留新结构并不是完整回退。恢复旧备份会替换当前业务数据并撤销旧凭据／授权，也可能丢失备份之后的新记录；先另行备份现状、核实恢复目标与数据缺口，再由维护人员使用对应旧版的受控恢复流程。任何恢复都应先在隔离副本演练，不能把本站配置或备份用于其他网站。
